# システム運用・復旧（開発版）

## バックアップと復元

システム管理者でログインして「システム保守」を開きます。「DBをバックアップ」でSQLiteファイルをダウンロードできます。復元はバックアップファイルを選択して実行します。復元時には投稿を一時的に停止し、復元前のDBもサーバー上にバックアップします。復元後は再ログインしてください。

CSVによる参加者の個人ログ出力は時刻とコメント本文のみ。ルーム管理者の全件CSVにはフォーム回答を含みます。

## 管理者のログイン情報を忘れた場合

システム管理者が利用できるなら「システム保守」から対象の管理者認証情報を再発行します。ルーム管理者は担当ルームの利用者コード再発行ができます。

システム管理者全員がログインできない場合は、エンジニアがサーバーの非公開 `storage/emergency-proof.txt` にランダムな小文字16進数64桁を作成し、`https://設置先/emergency-recover.php` で同じ値を入力します。対象のシステム管理者を選び、新しい認証コードを発行します。旧コードと認証セッションは使えなくなります。復旧ファイルは成功時に自動削除されます。

この非常復旧にはサーバーのファイル操作権限が必要です。固定された裏口の認証情報はありません。

## テストとセキュリティ

テストはGitHub ActionsでPHP 8.3/8.4の構文チェックとSQLiteの基本機能を確認します。これだけで本番環境の安全性は保証できません。共有レンタルサーバーでの実機設置、Cookie、ファイル権限、バックアップのデータ移行、更新・復旧のE2Eテストが必要です。

## アプリ本体の更新（署名付きZIP）

エンジニアが最初にEd25519公開鍵を非公開 `config.php` の `update.public_key` に設定し、リリース作成権限があるGitHub Actionsに対応する秘密鍵を登録します。通常の管理者は管理画面の「システム保守」→「署名付きZIPで更新する」でReleasesから取得したZIPと `.sig` をアップロードします。署名が一致しないZIPは適用されません。更新時は投稿を一時停止し、旧コード・DBのバックアップを作成します。失敗時は自動復旧を試みます。復旧不能な場合、`storage/maintenance.update` を残してアクセスを停止するため、エンジニアがバックアップを確認してください。自動適用を前提とした本番運用は、十分な実機検証を終えるまで行わないでください。
